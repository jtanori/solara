# 5. English and Spanish

## What is implemented

The language switcher stores `en` or `es` in the `solara_locale` browser cookie (one year, `SameSite=Lax`); English is the default. Server-rendered pages read that cookie and set the HTML language. The selected language is also used for Stripe Checkout and generated PDFs. Currency is independent of language: MXN is the default even in English. There is no translation API or locale-specific secret.

Canonical sign identifiers in chart data remain English. Editorial keys use the normal key for English and an `-es` suffix for Spanish; owners/editors can edit Sun, Moon, Ascendant and house notes separately in `/admin`.

## Local setup

1. Run the app, use the EN/ES selector in the header, and reload. Check the landing page, onboarding, account, pricing, chart and PDF in both languages.
2. Provision a local owner through the controlled process in the foundation guide; open `/admin`, choose the content language and edit a synthetic note. Check the matching reading and PDF. Edits go live immediately; there is not yet an approval workflow.
3. Test date formatting, accents, long strings, keyboard navigation and Stripe's selected language. The app does not automatically infer a locale from the browser or use locale-specific URL prefixes.

## Staging setup

1. Use the staging database and synthetic accounts. Have fluent reviewers check UI copy and both versions of each editorial interpretation.
2. Verify locale persistence across navigation, login and Checkout return; test both PDF editions and the mobile layout. Verify staging edits do not affect production content.
3. Document any missing translation or content-review process before promotion. Application copy ships with code; editorial notes live in the environment's database and are not automatically promoted between environments.

## Production setup

1. Publish reviewed ES/EN copy and establish an editorial approval/versioning process before promising stable reports. Do not copy production personal data into staging to test language changes.
2. Verify cookie/consent disclosures with counsel and monitor untranslated strings and accessibility. Check emails and legal copy if they are added later; this prototype does not yet provide a complete transactional-email system.
3. Treat language and currency independently when setting prices and support policies. No i18n environment variables are required.
